01 · Leitura executiva

O que o Mosaic já é

Não é só um chatbot. O repositório apresenta uma base local-first com estado persistente e um caminho de Agent/tool calling. A auditoria é estática: não executei backend, frontend nem testes nesta sessão.

No código

Provider + tool calling

Não validado aqui

Runtime integrado

O código sugere o fluxo e testes existem no repositório, mas build/testes e jornada end-to-end não foram executados.

Limite de evidência: “existe arquivo”, “há teste escrito”, “teste passou” e “fluxo completo validado” são estados diferentes. Este documento comprova leitura estática do main, não aprovação operacional.

04 · Fluxo do chat

Chat conversacional: resposta direta

O chat normal é distinto do Task Agent Loop, para que nem toda mensagem vire uma execução agentic.

1. POST chatconversation_id + content.
2. Persistir usuárioValidar conversa e modelo associado.
3. Build contextIdentidade, contexto relevante e histórico limitado.
4. OllamaGeração normal ou streaming via provider.
5. Persistir respostaMensagem assistente e retorno à UI.
Arquivos: api/chat.py → services/chat.py → context/manager.py → providers/ollama.py e repositórios de mensagem.
Entrada via UI

frontend/src/api.js implementa requests e SSE; App.jsx monta interface.

Persistência

Conversa e mensagens são armazenadas em SQLite. O modelo configurado na conversa determina provider/modelo.

Streaming

/conversations/{id}/chat/stream envia eventos SSE e [DONE]; erros são enviados como eventos de erro.

05 · Identidade e memória

O que torna Mosaic contínuo

A identidade canônica e os registros de memória pertencem ao Core; não dependem da conversa inteira estar no prompt.

Identidade

identity.py define MOSAIC_IDENTITY, afirmando que o modelo gera respostas, mas não é sozinho a identidade nem a memória. Trocar provider não deve apagar dados mantidos pelo Core.

Canônica no código

Memória explícita

memory/manager.py identifica pedidos “salve/guarde/lembre” sem exigir chamada ao modelo; persiste tipo, chave, valor, origem, escopo de projeto e confiança opcional.

Manager + repository

Classificação observada

TipoIntençãoCuidado
user_preferenceGosto, prefiro, preferência.Preferência não é fato externo.
user_claimOpinião, inferência ou afirmação informada pelo usuário.Afirmação continua claim até verificação independente.
instructionPedido persistido para agir/responder de certa forma.Não pode sobrepor política do Core.
project_state / registrosMemórias e estado usados pelo Context Manager.Fonte, escopo e atualidade têm que acompanhar.
Regra importante: o Context Manager injeta memórias como “records, not verified facts”. O harness deve manter tipo, fonte, escopo e atualidade na recuperação; um registro não vira verdade universal automaticamente.
06 · Context / RAGNES

Montagem do contexto

O Context Manager monta o prompt; RAGNES é descrito nos contratos como evolução da seleção/recuperação, não um segundo Core.

Identidade / instruçõesIdentidade canônica e regras aplicáveis.
Escopo do projetoEstado e memórias do projeto, quando relevantes.
Histórico limitadoMensagens recentes; antigas podem virar resumo.
Task + tool resultsEstado ativo e observações selecionadas.
Contexto enviadoMensagem atual no final do pacote.

Limites encontrados no código

  • Histórico recente: 20 mensagens.
  • Resultados de tools: limite configurado de 5, até 3.000 caracteres por resultado.
  • Contexto da Task: 4.000 caracteres.
  • Instruções do projeto: limite em bytes configurado.
  • Artefatos explicitamente solicitados: limites por quantidade, linhas e caracteres.

Contexto do Agent

services/agent.py usa contexto “objective-first”: histórico anterior só entra para pedidos detectados de continuidade/recall; estado/memória são incluídos conforme o objetivo. Plano e subtask atual podem restringir ferramentas, inclusive nenhuma em etapas de conteúdo.

Regra arquitetural: histórico persistido não equivale a tudo que vai ao modelo. Contexto deve ser selecionado, limitado e rastreável. Resumo nunca substitui fonte canônica.
07 · Harness observado

Agent Loop do Mosaic

Fluxo derivado de services/agent.py, agent_decision.py e services/tools.py. Descreve o código; não é afirmação de testes passados.

1. Iniciar TaskPOST /tasks/start ou /tasks/{id}/run.
2. Montar contextoObjetivo, etapa e observações reidratadas.
3. Decidir com providerCatálogo tools + tool calling do Ollama.
4. Política + toolSchema, workspace, aprovação e ToolResult.
5. Observar / fecharEvento persistido; loop continua ou conclui.

1. Iniciar Task

A API persiste o pedido como mensagem, cria Task agent-mode, marca executing e agenda o worker local.

Task API

api/tasks.py contém início, execução, cancelamento, eventos e decisão de aprovação/rejeição. O worker usa run_agent(task_id, create_provider_decider(task_id)).

Decisão do modelo

agent_decision.py monta catálogo de tools, lê provider/modelo da conversa, solicita decisão e valida resposta. O prompt do agente exige tool calling nativo e uma chamada por turno, com tentativas limitadas de correção.

Execução

services/tools.py resolve workspace, resolve política, valida argumentos, persiste ToolCall/ToolResult e aplica aprovação requerida.

Observação

agent.py limita iterações, reintroduz observações, pagina leituras deterministicamente e tem auxiliares de verificação de fontes/artefatos.

Aprovação / retomada

Há caminho de aprovação/rejeição de ToolCall persistida e retomada do mesmo Task; consistência sob corrida, erro ou reinício precisa ser provada por testes dinâmicos.

09 · Controles

Segurança: o que olhar com lupa

Controles estão distribuídos entre schemas, services, tools e estados. Segurança não deve depender só das instruções do modelo.

Controles visíveis

  • Filesystem resolve workspace e rejeita traversal/symlink.
  • Política de tool central em resolve_tool_policy.
  • Validação de argumentos e aprovação persistida.
  • Transições de Task e Action.
  • ToolResult vinculado à chamada.
  • Task events com sanitização de metadados.
  • Timeout e limite de saída de terminal no código de tools.

Validações ainda necessárias

  • Sandbox OS / privilégios / rede do terminal além de workspace e allowlist.
  • Redirecionamentos DNS/HTTP e limites de resposta.
  • Race conditions entre cancelar, aprovar, executar e retomar.
  • Não duplicar efeitos após falha ou reinício.
  • Redaction de args/result/eventos e proteção de segredos.
  • Se sair do uso local single-user, autenticação e escopo dos endpoints.
Boa separação: modelo propõe; Core valida; ferramenta executa; resultado persiste; modelo observa. A parte crítica é consistência sob falhas, não apenas o caminho feliz.
